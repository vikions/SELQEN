# SELQEN — research and implementation decision

Historical research snapshot: 2026-09-18. Implementation was subsequently approved and the mainnet MVP is now implemented. Statements about unimplemented features, endpoint availability and event dates below describe this research date, not current release status. See [README](../README.md) and [coverage](coverage.md) for current scope and dated validation evidence.

**Know what you're signing.**
**Browser safety layer for Robinhood Stock Tokens.**

## 1. Recommendation: MODIFY, then BUILD

Keep the Robinhood Chain focus and browser extension product. Narrow the first release to an independently verified asset/quote review, one explicitly supported Uniswap flow, a generic checker, and a deterministic demo. Do not promise universal signature interception or transaction enforcement. Morpho is a second milestone.

## 2. Why

Address provenance and corporate-action-adjusted valuation are real integration requirements, and public endpoints are accessible. The differentiator is explaining these together in the user's transaction context. Demand and retention remain product hypotheses; interview 3–5 target users during development and measure whether they understand the verdict and its scope.

## 3. Competitors

- [Pocket Universe](https://www.pocketuniverse.app/): direct category competitor for browser-based pre-sign warnings. Its public supported-chain list does not establish Robinhood Chain support.
- [Blockaid](https://blockaid.io/transaction-security): adjacent transaction simulation and screening infrastructure.
- HackQuest submissions: [SAGE](https://www.hackquest.io/zh-cn/projects/SAGE) describes token allowlists and wallet risk guards; [LP Guardian](https://www.hackquest.io/projects/LP-Guardian) describes LP risk management; [VetoVault](https://www.hackquest.io/projects/VetoVault) targets agent execution constraints; [ShortStack](https://www.hackquest.io/projects/ShortStack) targets stock-token lending. These descriptions were researched, not their implementations audited.
- [Robeon](https://www.robeondefi.com/whitepaper) describes a Robinhood-focused wallet and transaction explanations; a wallet is an adjacent distribution competitor.

No exact equivalent combining canonical registry, multiplier transitions and quote-context review was established in the searched public submissions. This is not proof of uniqueness or an exhaustive Singapore submission inventory.

## 5. Corrections to the prompt

- Runtime schema differs from prose docs: `tradingCapabilities` contains `market/extended/overnight`, with `whole/fractional` enum values, rather than only the documented flat nullable fields. Validate at runtime; unknown fields/states must not silently become ACTIVE. Add fixtures for both documented and observed forms.
- `/corporate-actions` returned IN_PROGRESS entries: it is not exclusively completed history. An announced action does not necessarily mean a pending multiplier has been scheduled.
- Tradability of the underlying is not the same as whether an ERC-20 transfer or DEX swap can execute. Display these separately.
- USD is not automatically USDG. Convert using a verified USDG/USD reference or label a parity assumption and withhold full economic verification.
- A DOM quote is an untrusted proposal, not evidence of actual calldata or a signature payload. Unknown units, addresses, routes or payloads result in partial coverage, never transaction VERIFIED.
- A green identity result must not imply approval safety, liquidity safety or safe signing.
- Opening a side panel requires a user gesture; populate an already-open panel automatically, otherwise offer an action/badge. [Chrome Side Panel API](https://developer.chrome.com/docs/extensions/reference/api/sidePanel).

## 6. Recommended MVP

Ship an unpacked MV3 extension, verdict-first side panel, generic address checker, live Robinhood client, deterministic safety engine, USDG quote comparison, JSON receipts and one Uniswap adapter. Include OBSERVE and GUARD warnings with explicit coverage labels. No secrets, custody, signing, telemetry or automatic transaction modification.

GUARD is an advisory interstitial for tested flows, not a universal wallet firewall. User continuation must remain explicit; do not replay or duplicate requests. If exact pre-sign binding cannot be demonstrated, ship that path as quote review, not signature protection.

Morpho collateral checking is stretch scope. [Morpho's official network dashboard](https://data.morpho.org/chain/robinhood-chain) shows stock-token collateral and USDG markets, but a specific interactive stock-token market flow has not been validated here. [Uniswap's announcement](https://blog.uniswap.org/pt-BR/robinhood-chain-is-live) confirms chain support. Its [AAPL/USDG pool page](https://app.uniswap.org/explore/pools/robinhood/0xc748f4671a867db48b552f6b7650bf3255e05f80f00e3f7aad1b17ccb7898fdb) was indexed, but a browser swap/signature flow was not exercised. Neither adapter is implemented or proven yet.

## 7. Proposed architecture

Use a pnpm TypeScript workspace, React/Vite UI, viem read-only RPC, Zod boundary validation, decimal arithmetic/BigInt, and Vitest. These are proposed choices, not installed dependencies.

| Path | Responsibility |
|---|---|
| `apps/extension` | MV3 worker, isolated content script, side panel, bounded message protocol |
| `apps/demo-lab` | Explicit LOCAL FIXTURE scenarios, synthetic clock, controlled preflight flow |
| `packages/engine` | Pure `evaluate(snapshot, intent, policy, now)`; no IO |
| `packages/robinhood` | Registry, REST normalization, RPC, verified feed configuration |
| `packages/adapters` | Uniswap extraction; Morpho only after feasibility gate |
| `packages/sdk` | Orchestration and receipt serialization |
| `packages/ui` | Shared verdict/reason/evidence components |
| `docs` | Sources, coverage matrix, threat model, demo and installation guide |

Pipeline: untrusted page intent → validated extension message → worker-owned API/RPC reads → normalized evidence → pure engine → side panel + receipt. Page messages cannot select arbitrary fetch URLs, mark evidence trusted, or enable fixture mode. Production and demo builds/configurations stay separate. Clear prior verdicts on navigation, chain/amount/token changes, expiry and worker restart; cancel or ignore outdated responses.

Snapshot groups: identity `{chainId,address,assetId,canonical,registryFetchedAt}`; values `{bid,ask,currency,currentMultiplier,pendingMultiplier,effectiveAt}`; state `{assetStatus,tradingCapabilities,halt,oraclePaused}`; oracle `{address,answer,decimals,updatedAt,blockNumber,sequencerState}`; provenance `{source,fetchedAt,generatedAt,mode}`. Unknown is distinct from false. Intent includes address pairs, amount in raw token units, displayed amount/units, expected output, minimum received, observedAt, optional true quote timestamp, target, route and payload digest when available. Never substitute observedAt for quoteGeneratedAt.

For a sell reference: raw token quantity × multiplier × equity bid ÷ USDG USD price. Report a reference value/range, not a guaranteed executable price. Separate quote deviation, slippage minimum, network costs, fees and liquidity effects. Split-transition snapshots must be coherent; never multiply a pre-split price by a post-split multiplier.

Receipt includes schema/policy versions, coverage, source mode, timestamps, addresses, chain, snapshot, intent hash when known, checks and reason codes. Export is a local record, not an issuer-signed attestation.

Permissions: `sidePanel`, `storage`; explicit supported-site content-script matches and only required API/RPC hosts. Optional Morpho host access only when shipped. Generic checker accepts manual addresses without all-sites browsing access. Network reads originate in the worker, with fixed destinations and bounded messages. [Chrome network guidance](https://developer.chrome.com/docs/extensions/develop/concepts/network-requests).

Pre-sign feasibility spike: one selected injected wallet, EIP-1193 request capture, EIP-6963 discovery, and an explicitly supported Uniswap route. Inspect transaction requests and typed-data permits/orders; unknown payloads remain unverified. WalletConnect, arbitrary routers, smart-account batches and universal wallet coverage are outside the initial claim. Provider discovery does not grant a trusted interception boundary. [EIP-1193](https://eips.ethereum.org/EIPS/eip-1193), [EIP-6963](https://eips.ethereum.org/EIPS/eip-6963).

## 8. Deterministic 3-minute demo

0:00–0:35: two AAPL-labelled assets; canonical-address evidence versus a clearly labelled local noncanonical fixture.

0:35–1:15: real extension alongside Uniswap; live canonical metadata and reference pricing if fresh and accessible. Clearly label page quote coverage; never imply it is decoded calldata.

1:15–2:00: LOCAL FIXTURE pending action → oracle pause → mismatched transition quote → request to refresh. Use a coherent split sequence so a multiplier change does not manufacture a gain.

2:00–2:35: fixture proposed USDG settlement materially below the reference; explain that fees/liquidity may contribute. Show GUARD warning and user-controlled continuation in the controlled flow.

2:35–3:00: export the receipt with fixture/live provenance. Show stale-data failure if time permits. Morpho is optional, not necessary to explain the product.

## 9. Live versus fixtures

Live verified in research: REST endpoints and chain-ID reads. Live documented but not yet exercised: token multiplier RPC methods, Chainlink feeds, USDG contracts, dApp adapters. Deterministic fixtures: impersonator, pending action, pause, stale source, wrong chain and bad quote. Any unavailable live dependency produces DATA UNAVAILABLE or limited coverage; never silently substitute fixtures.

## 11. Highest-risk blockers and contract decision

Technical: matching a mutable dApp quote to the actual wallet request. Start here with a strict time box; downgrade to clearly labelled quote review if coverage cannot be established.

Data: feed proxies/heartbeats and session-aware freshness still need runtime verification. A missing oracle cannot silently count as a successful check.

Eligibility: [event rules](https://www.hackquest.io/hackathons/Arbitrum-Open-House-Singapore-Online-Buildathon?tab=custom-dfc39bda-c613-4658-8df9-f35b527dace5) require deployment on an Arbitrum chain. Pure read-only extension eligibility is unresolved. No message has been sent to organizers.

Recommended product architecture is extension + SDK, without a settlement contract in phase one. A receipt-hash logger or demo token deployed only for eligibility would be artificial and would not establish eligibility. A meaningful alternative is a separately opted-in atomic settlement module enforcing user-defined token, recipient, deadline and minimum-output constraints. It requires genuine routed execution, tests and its own scope; it does not protect arbitrary Uniswap trades automatically. Decide after product approval and eligibility clarification. No contract deployment is authorized by this report.
